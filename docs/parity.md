# 界面与命令行的功能对等

本文是**硬约束**，不是建议：CLI 能做而 TUI 做不到的功能，一律视为缺陷。

## 1. 三条规则

1. **能力对等**：`cx` 子命令能完成的事，TUI 里必须有入口；两者走**同一份实现**，
   不允许界面自己再写一套逻辑（现在通过 `cx_tui::BackendAdmin` 之类的回调注入，
   见 §3）。
2. **风险要问，不要教**：不可逆或影响面大的动作必须停在确认页，
   `y`/`回车` 才执行，其他任意键取消。**不许**"打一行提示让用户回命令行"
   （曾经这样处理"已有空间时按 `s`"，被判定为缺陷）。
3. **界面只放四类东西**：值、状态、按键、以及**会改变决定的那一句后果**。
   解释"为什么这样设计""应该怎么做"的文字属于文档，不属于界面。

### 2.2 尚未对等（明确的待办，不是"设计如此"）

| CLI | 状态 | 说明 |
|---|---|---|
| `cx config show/path/check` | 待定 | 配置页已能改逐个键；`show`（整份 TOML）与 `path`（配置文件路径）更适合命令行查看，`check` 已被面板「需要处理」覆盖 |
| `cx stop` | 待定 | 退出界面只结束本地客户端，守护进程仍在后台同步；是否在界面里"停掉守护进程"需要产品决定（会真的停止同步） |

### 2.3 明确的例外（不需要对等）

| CLI | 理由 |
|---|---|
| `cx --json`、`--quiet`、`cx status --json` | 给脚本/管道用的机器输出，交互界面里没有意义 |
| `cx daemon`（前台运行） | 进程管理入口，被 systemd / LaunchAgent 调用 |
| `cx version` | 界面里已经在状态栏展示 |

## 3. 新增能力时的落地清单

对等不是自动产生的，加功能时按这个顺序做，少一步就会出现"CLI 有、TUI 没有"：

1. **实现**：逻辑放 `cx-cli`（或更下层），不要写在 `cx-tui` 里。
2. **暴露**：在 `cx_tui::BackendAdmin`（或新的 trait）加方法，返回
   `Result<String, String>`——成功/失败都只是给人看的一行话。
3. **意图**：在 `App` 里加 `KeyOutcome` 变体；按键处理只负责"产出一个意图"，
   不碰文件系统、不碰网络。
4. **风险**：破坏性动作前先设置 `pending_*` 状态并渲染确认页，`y`/`回车` 才转成
   真正的 `KeyOutcome`。
5. **页面**：整屏（`let popup = area;`），标签列表格或"标签 + 值"两列；只写
   §1 允许的四类内容；长文本/长密钥按显示列折行，**不截断**。
6. **测试**：
   - `app.rs`：按键 → 意图（含"该确认的确实停在确认页"）；
   - `ui.rs`：页面渲染断言（含"内容完整"这类不变量，例如密钥 64 位拼得回来）；
   - 如涉及文件：在 `cx-cli` 里加临时目录往返测试。
7. **文档**：更新本文件 §2 与 `README.md` 的按键表。

## 4. 已知的界面取舍

- **一次只画一页**：面板、表单、帮助、确认、输入都是整屏，不做叠窗——
  小终端下叠窗会互相遮挡（曾经出现过提示文字从边框缝里漏出来）。
- **提示只画在主界面**：整屏页面打开时不画头部提示，结果行只在页面内部出现一次。
- **不把主密钥放进剪贴板**：剪贴板本身是被同步的内容，放进历史并上传等于把钥匙
  散播出去；导出走文件（0600）。
